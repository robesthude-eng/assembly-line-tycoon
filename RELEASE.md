# Выпуск версий

## Как устроена версия

Версия задаётся в одном месте — `version.properties` в корне проекта.

```properties
VERSION_MAJOR=0
VERSION_MINOR=1
VERSION_PATCH=0
VERSION_BUILD=1
```

Из них собираются два числа:

* `versionName` — то, что видит игрок: `0.1.0`
* `versionCode` — то, по чему Android решает, что это обновление:
  `мажор × 10 000 000 + минор × 100 000 + патч × 1 000 + номер сборки`

Для `0.1.0` сборки 1 это `100001`. Схема гарантирует, что номер **строго растёт**:
`0.1.0` (100001) → `0.1.0` сборка 2 (100002) → `0.1.1` (101001) → `0.2.0` (200001).

В CI номер сборки подменяется счётчиком прогонов GitHub Actions
(`GITHUB_RUN_NUMBER`), поэтому каждая сборка получает свой `versionCode`
автоматически — руками ничего трогать не нужно.

Проверить, что получится:

```bash
./gradlew printVersion
```

## Повышение версии

```bash
./gradlew bumpBuild    # 0.1.0 (1) → 0.1.0 (2)   — пересборка того же
./gradlew bumpPatch    # 0.1.0    → 0.1.1        — исправления
./gradlew bumpMinor    # 0.1.3    → 0.2.0        — новая механика
./gradlew bumpMajor    # 0.9.1    → 1.0.0        — крупный релиз
```

Правило: `version.properties` меняется только этими задачами. Ручная правка
легко даёт `versionCode` меньше уже опубликованного — и обновление перестаёт
устанавливаться, причём молча.

## Сборка релиза

**Через GitHub Actions** (основной путь) — вкладка Actions → workflow
**Release** → Run workflow → выбрать, что повысить. Пайплайн прогонит тесты,
соберёт подписанные APK и AAB, зафиксирует новую версию коммитом и выложит
файлы в артефакты прогона.

Второй способ запуска — пуш тега:

```bash
git tag v0.2.0 && git push origin v0.2.0
```

По тегу дополнительно создаётся GitHub Release с приложенными APK и AAB.

**Локально:**

```bash
./gradlew :app:assembleRelease   # APK для установки на устройство
./gradlew :app:bundleRelease     # AAB для загрузки в RuStore
```

Готовые файлы: `app/build/outputs/apk/release/app-release.apk` и
`app/build/outputs/bundle/release/app-release.aab`.

## Подпись

Ключ подписи — это то, что позволяет обновлению встать поверх установленной
игры. Android проверяет: если подпись другая, установка отклоняется с
`INSTALL_FAILED_UPDATE_INCOMPATIBLE`, и игроку приходится удалять игру вместе
с прогрессом. **Ключ нельзя терять и нельзя менять** — восстановить его
невозможно, а RuStore не примет обновление, подписанное другим ключом.

Хранилище: `artifacts/assembly-line-tycoon-release.jks`, алиас
`assemblylinetycoon`, RSA 4096, срок действия 30 лет.
Файл в `.gitignore` — в репозиторий он не попадает.

Локальная сборка берёт пароли из `keystore.properties` (тоже не в репозитории):

```properties
storeFile=artifacts/assembly-line-tycoon-release.jks
storePassword=…
keyAlias=assemblylinetycoon
keyPassword=…
```

Если файла нет, `assembleRelease` не падает, а выдаёт неподписанный APK —
локальная сборка работает у любого разработчика без доступа к ключу.

CI берёт ключ из секретов репозитория (уже настроены):

| Секрет | Что внутри |
|---|---|
| `KEYSTORE_BASE64` | сам `.jks`, закодированный base64 |
| `KEYSTORE_PASSWORD` | пароль хранилища |
| `KEY_ALIAS` | `assemblylinetycoon` |
| `KEY_PASSWORD` | пароль ключа |

Пересоздать значение для секрета, если понадобится:

```bash
base64 -w0 artifacts/assembly-line-tycoon-release.jks
```

## Почему релиз не встаёт поверх отладочной сборки

У debug-сборки другой идентификатор приложения: к `applicationId` добавляется
суффикс `.debug`. Для Android это **другое приложение**, поэтому релиз не
обновит его, а установится рядом.

| Сборка | applicationId | Подпись |
|---|---|---|
| debug | `com.example.assemblylinetycoon.debug` | отладочный ключ |
| release | `com.example.assemblylinetycoon` | ключ проекта |

Так сделано намеренно: отладочная и «боевая» версии живут на устройстве
одновременно, каждая со своим сохранением. Перед установкой релиза отладочную
сборку нужно удалить (или просто оставить — она не мешает).

Дальше обновления релиза поверх релиза устанавливаются штатно: тот же
`applicationId`, тот же ключ, больший `versionCode`.

## Перед публикацией в RuStore

* [ ] Сменить `applicationId` с `com.example.…` на реальный —
      `com.example.*` в магазины не принимают
* [ ] Подставить настоящие идентификаторы блоков Yandex Ads и
      `consoleApplicationId` RuStore вместо заглушек
* [ ] Проверить экран согласия на обработку данных (152-ФЗ) до инициализации
      рекламного SDK
* [ ] Загружать `.aab`, а не `.apk` — RuStore поддерживает оба формата, но
      бандл весит меньше для игрока
* [ ] Сохранить keystore в надёжном месте отдельно от репозитория
