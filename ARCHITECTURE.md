# Архитектура

Документ фиксирует правила, нарушение которых считается ошибкой на ревью.
Он важнее конкретного кода: код меняется, правила — нет.

## Слои и направление зависимостей

```
presentation ──▶ domain ◀── data
     │             ▲          
     └──▶ core ◀───┴── monetization
```

* **domain** не зависит ни от кого, кроме `core`, Kotlin и `kotlinx.*`.
  В нём **нет ни одного импорта `android.*`** — это проверяемое правило.
* **data** реализует интерфейсы домена поверх DataStore.
* **monetization** реализует интерфейсы домена поверх Yandex Ads и RuStore Billing.
* **presentation** знает домен, но не знает data и monetization.
* **app** — единственное место, где всё связывается (`AppContainer`).

Почему так: рекламную сеть, хранилище и даже UI-фреймворк можно заменить,
не трогая правила игры. Для проекта, который переживёт смену SDK и магазинов, это
не абстрактная красота, а условие выживания.

## Однонаправленный поток данных

```
пользователь
    │  GameIntent
    ▼
GameViewModel ──── GameCommand ───▶ GameEngine (GameLoop)
    ▲                                    │
    │  StateFlow<GameUiState>            │  StateFlow<GameState>
    │                                    ▼
Compose UI ◀───────────── проекция состояния
    │
    └── FactoryCanvas: только рисует, ничего не меняет
```

Правила:

1. **`GameState` — единственный источник правды** симуляции.
   Никаких дублирующих счётчиков в UI или ViewModel.
2. **Мутация состояния возможна только в `GameLoop.reduce`.** Это чистая функция
   `(состояние, команда) → новое состояние`.
3. **ViewModel не считает экономику.** Он проецирует `GameState` → `GameUiState`
   и переводит интенты в команды.
4. **Canvas — только отрисовка.** Рендерер получает состояние и колбэк тапа.
   Он не хранит игровые данные и не вызывает движок напрямую.
5. **Разовые действия — эффекты, а не состояние.** Показ ролика лежит в
   `SharedFlow<GameEffect>`; в `UiState` его класть нельзя, иначе реклама
   повторится при повороте экрана.
6. **Состояние наружу — только неизменяемое.** `MutableStateFlow` приватен,
   публичен `StateFlow`.

## Потоки исполнения

| Что | Где выполняется |
|---|---|
| Тик симуляции (50 мс) | `Dispatchers.Default` (`GameLoop`) |
| Чтение и запись DataStore | `Dispatchers.IO` (репозитории) |
| Проекция состояния и Compose | main |

Главный поток никогда не считает симуляцию: при сотнях предметов на конвейере
это единственный способ удержать 60 FPS.

## Время

Игра не берёт время из `System.currentTimeMillis()` напрямую — только через
`TimeProvider`. Две причины: детерминированные тесты и защита от перевода
системных часов (классическая накрутка офлайн-дохода). Тикер использует
монотонное время, сохранения — настенное.

## Сохранения

* Формат — JSON через `kotlinx.serialization`, типизированный DataStore.
* `ignoreUnknownKeys = true` и `encodeDefaults = true` обязательны: сохранение
  старой версии обязано открыться в новой сборке.
* Повреждённый файл не роняет игру: `ReplaceFileCorruptionHandler` возвращает
  состояние новой игры.
* Схема версионируется (`GameConstants.SAVE_SCHEMA_VERSION`), миграции живут
  в `GameStateMapper`.
* Автобэкап Android выключен: восстановление чужого снапшота ломает экономику.

## Монетизация

* Домен видит только `AdsRepository` и `BillingRepository` — никаких типов SDK.
* Рекламный SDK инициализируется **после** экрана согласия (152-ФЗ), поэтому
  инициализация вынесена в явный шаг `AdsInitializer`, а не в `Application.onCreate`.
* Закрытие ролика до конца не тратит кулдаун плейсмента.
* Покупка «Без рекламы» не отбирает бонусы: она выдаёт их бесплатно.
* `MainActivity.onNewIntent` пробрасывает интент в биллинг — без этого возврат
  из платёжного флоу RuStore зависает.

## Чего в проекте намеренно нет

| Решение | Причина |
|---|---|
| DI-фреймворк (Hilt/Koin) | граф маленький, кодогенерация замедляет сборку; `AppContainer` покрывает потребности |
| Room | состояние — один снапшот, а не таблицы; DataStore проще и быстрее |
| Несколько Activity | игра — один экран с навигацией внутри Compose |
| `dynamicColor` Material You | системная перекраска ломает связку HUD и Canvas |
| Игровая логика в Compose | пересчёт симуляции в рекомпозиции — гарантированные просадки FPS |

## Как добавлять новое

1. Модель и правило — в `domain`.
2. Хранение — реализация интерфейса в `data`.
3. Команда движку — новый вариант `GameCommand` + ветка в `reduce`.
4. Экран — «глупая» Composable-функция + `@Preview`, состояние приходит параметром.
5. Действие пользователя — новый `GameIntent`, обработка в `handleIntent`.


## Слой данных баланса (этап 2)

Справочники (`domain/catalog`) отделены от состояния (`domain/model`) намеренно.

* **В сохранение попадает только состояние**: идентификаторы предметов,
  количества, уровни, координаты. Цены, длительности и рецепты живут в коде.
* Следствие: правку баланса можно выкатить обновлением приложения, и старые
  сохранения продолжат открываться. Обратный подход — «сериализовать рецепты
  в сейв» — привязал бы игроков к балансу той версии, в которой они начали.
* Каталоги — `object` без состояния и без Android-зависимостей, поэтому
  проверяются обычными JVM-тестами за доли секунды.

### Почему баланс проверяется тестами

`CatalogIntegrityTest` — это не тест кода, а тест данных. Он падает, если:

* предмет нельзя получить ни одним рецептом;
* вход рецепта того же или более высокого яруса, чем выход (цикл в цепочке);
* передел убыточен или его маржа ниже 10%;
* такт вышел за проектный диапазон 2–25 с;
* рецепт закреплён за машиной, которая его не умеет.

Ошибки такого рода не ловятся компилятором и в ручном тестировании всплывают
только через час игры, поэтому дешевле поймать их за 200 мс на сборке.

### Правила работы с числами

* Деньги — только `Long`. `Double` используется как промежуточное значение
  внутри `MathUtils`, округление выполняется ровно один раз, на выходе.
* Любое накопление денег идёт через `MathUtils.addCoins`: баланс не уходит
  в минус и упирается в `Long.MAX_VALUE` вместо переполнения в отрицательное.
* Длительность такта всегда проходит через `MathUtils.craftDuration`:
  пол в 100 мс не даёт апгрейдам обнулить время и сломать тик.


## Идентификаторы предметов: enum и строка одновременно

`ItemId` — перечисление, но в рецептах и сохранениях используется его
строковый `key` (`ItemId.IRON_ORE.key == "iron_ore"`), а входы рецепта имеют
тип `Map<String, Int>`.

Зачем два представления:

* **Строка в данных.** Ключ переживает переименование константы Kotlin и
  рефакторинг пакетов, поэтому сохранение, сделанное в версии 0.1, откроется
  в версии 2.0. Enum, сериализованный по имени, такой гарантии не даёт.
* **Enum в коде.** Каталог собирается через `Recipe.of(output = ItemId.GEAR,
  inputs = mapOf(ItemId.IRON_INGOT to 3), …)`: опечатка в идентификаторе —
  ошибка компиляции, а не пустой буфер во время игры.
* **Карта, а не список пар.** Требования рецепта сравниваются по ключам,
  поэтому «2 руды и 1 медь» и «1 медь и 2 руды» — один и тот же набор.
  Порядок вставки не влияет ни на `canCraftFrom`, ни на равенство рецептов.

Мост между представлениями — `ItemId.fromKey`, возвращающий `null` для
неизвестного ключа: данные из чужого сохранения не должны ронять игру.

## Округление в экономике

Формулы усекают дробную часть (`toLong()`), а не округляют:

```
Cost     = (BaseCost * 1.15^Level).toLong()
Duration = max(100L, (BaseDuration * 0.95^Level).toLong())
```

Усечение выбрано не из вкуса, а из свойства: цена, показанная игроку, никогда
не окажется ниже фактически списанной. Округление вверх на половине монеты
дало бы обратное — «стоит 152, списали 153», и это первое, о чём напишут в
отзывах. `Double` используется только как промежуточное значение внутри
`MathUtility`; наружу всегда выходит `Long`.

## Симуляция завода (этап 3)

Симуляция — чистый Kotlin: ни одного `import android.*`, никаких файлов и таймеров
платформы. Благодаря этому весь завод крутится прямо в юнит-тестах, а CI
отдельным шагом следит, что в `domain/` не появилось Android-зависимостей.

**Кто за что отвечает**

| Файл | Роль |
| --- | --- |
| `domain/engine/GameLoop.kt` | Корутинный тикер каждые 50 мс, хранит `StateFlow<GameState>`, принимает команды |
| `domain/engine/FactorySimulation.kt` | Чистая функция `step(state, deltaMillis): GameState` — весь ход времени на заводе |
| `domain/engine/OfflineProgressCalculator.kt` | Начисление за время, пока игра была закрыта |
| `domain/model/MovingItem.kt` | Предмет, едущий между клетками |
| `domain/model/ProductionStats.kt` | Накопительная статистика: произведено, заработано, отыграно времени |

**Единственный источник правды** — `GameState`: баланс, сетка, машины, едущие
предметы, статистика, отметка последнего сохранения. Движок ничего не рисует и
не знает о существовании UI.

### Порядок фаз внутри такта

1. **Машины** — приём сырья, такт крафта, выгрузка результата.
2. **Ленты** — движение предметов.

Именно в таком порядке: если сначала двигать ленты, свежевыгруженный предмет
успеет проехать клетку в том же такте, и скорость конвейера начнёт зависеть от
частоты кадров.

### Правила сетки

- Предмет едет строго по направлению ленты — **никакого поиска пути**.
- **Одна клетка — один предмет**. Целевая клетка считается занятой, пока к ней
  кто-то едет, поэтому предметы не «слипаются».
- Если ехать некуда, прогресс упирается в `1.0` и предмет ждёт: затор
  выстраивается в очередь, а не теряется.
- Предметы живут в `GameState.movingItems`, а не внутри клеток. Одно
  представление вместо двух — нечего рассинхронизировать.

### Машина: IDLE → CRAFTING → OUTPUT_EJECT

Смена фазы **не съедает такт**. Остаток дельты переходит в следующую фазу, и
машина может за один вызов доработать такт, выгрузить результат и начать новый.
Иначе результат симуляции зависел бы от частоты тиков: два шага по 100 мс
давали бы не то же, что один шаг 200 мс. Число переходов за такт ограничено
константой, чтобы никакая комбинация не зациклилась.

Роли машин: карьер (`isSource`) производит сырьё без входов, перерабатывающие
машины списывают входы рецепта, экспортёр (`isSink`) превращает изделие в монеты
по цене предмета. Все длительности берутся из существующего каталога рецептов и
`MathUtility.craftDuration` — новых экономических чисел этап не вводит.

### Детерминизм

Одинаковый вход даёт одинаковый выход: машины обходятся по возрастанию `id`,
предметы — по порядку списка, случайных чисел нет. Дельта обрезается сверху
(`MAX_TICK_DELTA_MS`), чтобы после сворачивания приложения завод не «прыгал»
сквозь занятые клетки; хвост времени просто досчитается следующими тактами.
Поэтому в тестах время проматывается тактами по 50 мс, а не одним большим шагом.

`BELT_TRAVEL_TIME_MS = 500` (две клетки в секунду) — константа скорости
анимации, а не экономики.

### Офлайн-прогресс

Считается от сохранённой отметки времени, а не от счётчика тиков: `начислено =
min(прошло, кап) × ставка × коэффициент`. Кап по умолчанию — 2 часа. Отметка
`0` означает «игра ещё ни разу не сохранялась» — за первый запуск не платим.
Переведённые назад часы дают ноль, а не отрицательный баланс.

## Слой представления (этап 4)

Правило слоя одно: **интерфейс только показывает состояние**. Симуляции в нём
нет ни в каком виде — ни в Compose-функциях, ни в рендерере, ни в ViewModel.

```
GameEngine.state ──► FactoryUiStateMapper ──► FactoryUiState ──► Compose
      ▲                                                             │
      └────────────── GameCommand ◄── FactoryViewModel ◄── FactoryIntent
```

| Файл | Роль |
| --- | --- |
| `presentation/state/FactoryUiState.kt` | Снимок экрана: баланс, производство, модель отрисовки, выбор, диалог, усиления |
| `presentation/state/FactoryIntent.kt` | Что сделал игрок: выбрал ячейку, открыл карточку, строит, улучшает, закрыл диалог |
| `presentation/mapper/FactoryUiStateMapper.kt` | Чистая проекция `GameState` → `FactoryUiState` |
| `presentation/viewmodel/FactoryViewModel.kt` | Подписка на движок и маршрутизация намерений — и больше ничего |
| `presentation/ui/render/FactoryGeometry.kt` | Пиксели ↔ клетки: чистая арифметика без Compose |
| `presentation/ui/components/FactoryCanvas.kt` | Отрисовка поля, лент, машин, едущих предметов |
| `presentation/ui/components/FactoryHud.kt` | Баланс, производство в минуту, плашка усилений |
| `presentation/ui/components/MachineDialog.kt` | Карточка машины и заготовка постройки |
| `presentation/ui/screens/FactoryScreen.kt` | Сборка экрана: HUD + холст + диалоги |
| `presentation/ui/screens/MainScreen.kt` | Корень приложения: тема и навигация |

### Почему проекция вынесена из ViewModel

`FactoryUiStateMapper` — обычный объект без Android-зависимостей, поэтому
перевод состояния проверяется JVM-тестом. ViewModel остаётся тонким: подписался,
спроецировал, передал намерение. Ни расчёта производства, ни движения
предметов, ни обработки рецептов в нём нет — иначе появился бы второй,
неизбежно расходящийся с движком источник правды.

Выбор ячейки и открытый диалог живут в `FactoryUiState`, а не в симуляции:
это состояние интерфейса, движку о нём знать незачем. Зато открытая карточка
пересобирается на каждом тике — иначе полоса прогресса в диалоге замерла бы,
пока завод продолжает работать.

### Рендерер

Canvas вместо дерева виджетов: на поле 10×10 одновременно едут десятки
предметов, и сотня перекомпоновок в кадре дороже одной отрисовки.

Что сделано ради кадров:

* геометрия и разметка подписей считаются в `remember` и переживают кадры —
  во время отрисовки происходит только чтение;
* цвета разобраны один раз в `FactoryPalette`, `#RRGGBB` из каталога не
  парсится на каждом кадре;
* `FactoryRenderModel` держит **ссылки** на неизменяемые доменные объекты,
  а не копии: новых списков на кадр не создаётся;
* уровень апгрейда рисуется точками, а не цифрой — измерение текста самая
  дорогая операция в этой отрисовке.

Рендерер ничего не меняет. Единственное, что он умеет наружу, — сообщить,
в какую клетку попал палец; перевод пикселей в координаты делает
`FactoryGeometry`, решение принимает ViewModel, состояние меняет движок.

### Постройка и улучшение

Интенты `PlaceMachine` и `UpgradeMachine` уже есть, но пока отвечают
сообщением «появится на следующем этапе»: обе операции списывают деньги,
то есть требуют новой команды движку, а движок на этом этапе не трогаем.
Экран к ним готов — не хватает только команды в домене.

### Тесты интерфейса

Compose-тесты идут через **Robolectric в обычной JVM**: эмулятора нет ни в
песочнице, ни в CI, а экран должен проверяться на каждом коммите. Размер
экрана зафиксирован в `@Config(qualifiers = ...)`, иначе геометрия холста
зависела бы от машины, на которой запущен тест.

## Постройка и улучшение (этап 4b)

`domain/engine/FactoryBuilder.kt` — чистые функции над `GameState`: постройка,
улучшение и предикаты «можно ли». Отделено от `FactorySimulation` потому, что
это разные вещи: там время течёт само, здесь состояние меняется по воле игрока.

Поток данных обычный:

```
тап по пустой ячейке → FactoryIntent.PlaceMachine → GameCommand.PlaceMachine
   → FactoryBuilder.place → новый GameState → StateFlow → экран
```

**Цены живут только в каталоге.** `FactoryBuilder.buildCost` спрашивает
`MachineCatalog.buildCost`, диалог магазина спрашивает `FactoryBuilder`, движок
при списании — его же. Ни одна формула стоимости не переписана заново: иначе
цена в магазине и цена при списании однажды разойдутся, и игрок увидит списание
не той суммы, которую нажимал.

Отказ выражается **возвратом того же самого состояния** — движок не умеет
показывать диалоги. Чтобы нажатие не выглядело сломанным, экран заранее
спрашивает `canPlace` / `canUpgrade`: не хватает денег — гасит строку и
показывает сообщение, а команду не отправляет. Проверка и списание используют
один и тот же предикат, поэтому разойтись не могут.

Принятые правила:

* цена растёт **по типам независимо**: вторая плавильня дороже первой, но на
  цену пресса это не влияет;
* идентификаторы машин только растут — переиспользование номеров сломало бы
  ссылки из ячеек поля и открытых диалогов;
* построенная машина сразу получает первый рецепт своего типа: выбор рецепта
  игроком появится позже, а стоять без дела станок не должен;
* улучшение **не сбрасывает прогресс такта**: игрок платит за ускорение,
  и отматывать почти готовую деталь было бы наказанием за покупку.

### Чего пока нет

Постройка конвейера и снос. Цены ленты нет ни в GDD, ни в балансовой модели, а
придумывать её самостоятельно значит менять экономику — это отдельное решение,
а не побочный эффект этапа.

## Редактор завода: конвейер, поворот, снос (этап 4c)

Теперь завод собирается целиком внутри игры: лента, машины, разворот и снос —
всё через те же команды движку.

| Команда | Что делает |
| --- | --- |
| `PlaceMachine` | ставит станок, цена из `MachineCatalog` |
| `UpgradeMachine` | поднимает уровень, цена из каталога |
| `PlaceBelt` | прокладывает отрезок ленты, цена из `BeltCatalog` |
| `RotateBelt` | разворачивает ленту, бесплатно |
| `Demolish` | сносит содержимое ячейки, без возврата денег |

### Цена конвейера — дополнение баланса, а не находка в ТЗ

Ни в GDD, ни в «Economy & Balance Model» ленты нет: там описаны только машины.
Значения собраны в `BeltCatalog` и обоснованы прямо в коде:

* **база 10 монет** — дешевле самой дешёвой машины (карьер, 50). Иначе
  соединить два станка стоило бы дороже, чем поставить третий;
* **рост 1.03 за отрезок** — цена обязана расти, иначе «замостить поле лентами»
  становится безальтернативной стратегией. Множитель машин (1.15) здесь не
  годится: на поле 10×10 сотая лента стоила бы миллионы;
* **поворот бесплатен** — плата за поворот наказывала бы за исправление
  собственной ошибки и подталкивала сносить и класть заново.

Важное следствие правила проекта «цена усекается вниз»: 3 % от 10 монет меньше
монеты, поэтому цена ленты растёт **ступенями** — 10, 10, 10, 10, 11… Это
поймал тест, который сначала требовал строгого роста на каждом шаге. Поднимать
базу ради красивой монотонности не стали: это сделало бы ленту дороже ради
самой цены. Тест переписан на реальное правило — цена не падает никогда и за
поле вырастает более чем в пять раз.

### Снос без возврата денег

Возврат части стоимости — это ещё один экономический множитель, которого нет
в документах. Вводить его заодно со сносом значило бы протащить непроверенное
решение. Без возврата снос честно остаётся исправлением ошибки, а не способом
заработать на перестройке.

Предметы, ехавшие в снесённую клетку или из неё, исчезают вместе с ней: иначе
они зависли бы на несуществующей ленте и заблокировали соседей.

### Стартовый капитал

`GameState.NEW_GAME` даёт `GameConstants.STARTING_COINS = 200`. Раньше новая
игра начиналась с нуля монет на пустом поле — то есть первый же экран был
тупиком: строить не на что, зарабатывать нечем. Сумма подобрана под минимальную
работающую линию: карьер (50) + четыре ленты (~40) + экспортёр (100) = 190.
Тест строит эту линию по каталогам и проверяет, что баланс не уходит в минус, —
если цены изменятся, тест упадёт раньше игрока.

## Сохранение прогресса (этап 5)

До этого этапа сохранение существовало на бумаге: DataStore и сериализатор были
написаны, но прогресс записывался только при уходе с экрана, отметка времени не
проставлялась никем, а посчитанный офлайн-доход никуда не начислялся. Каждая из
трёх дыр по отдельности выглядит мелочью, вместе они означали простое: игрок
теряет завод, если система выгрузит приложение.

### Кто ставит отметку времени

`lastSavedAtMillis` проставляет `SaveGameStateUseCase`, а не вызывающий код.
Это единственная точка отсчёта офлайн-дохода, и если оставить её на совесть
каждого места вызова, рано или поздно появится путь сохранения без отметки —
и игрок либо не получит ничего за отсутствие, либо получит начисление за всё
время с прошлого раза.

### Порядок холодного старта

1. загрузка снапшота;
2. расчёт офлайн-дохода по нему — **до** запуска движка: после первого же тика
   `lastSavedAtMillis` перестанет описывать момент, когда игрок ушёл;
3. запуск движка;
4. начисление командой `ApplyOfflineEarnings` (ViewModel не трогает баланс
   напрямую даже здесь);
5. окно «Пока вас не было» — только если начислено больше нуля. Пустое
   «вы заработали 0» обесценивает механику;
6. запуск автосохранения.

### Автосохранение

Раз в `AUTOSAVE_INTERVAL_MS` (30 с), пока экран на переднем плане; останавливается
на `ScreenStopped` и в `onCleared`. Уход с экрана сохраняет отдельно и сразу:
следующим шагом система может убить процесс без предупреждения.

Тестовая тонкость, стоившая получаса зависшего прогона: цикл автосейва —
бесконечный `while(true) { delay(...) }`, и `advanceUntilIdle()` на нём **не
возвращается никогда**, потому что очередь виртуального времени не пустеет.
В тестах используется `runCurrent()` и `advanceTimeBy()`, а каждый тест,
запускающий экран, обязан его остановить.

### Что проверяется в формате сохранения

`GameStateSerializerTest` защищает то, что игрок не сможет восстановить сам:
построенный завод переживает круг «запись → чтение» без потерь, файл прошлой
версии читается новой сборкой, неизвестные поля из будущей версии игнорируются,
битый файл даёт `CorruptionException` и откат к playable-состоянию новой игры,
а не краш-луп на старте.
